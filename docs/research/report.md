### Выводы по обзору

Правила и словари помогают находить подозрительные формулировки и объяснять, почему фрагмент отмечен [6, 8, 12]. Для классификации требований применяют классические методы, включая SVM с лексическими и синтаксическими признаками [13], и модели на основе трансформеров, например NoRBERT [11]. RuBERT [14] позволяет проверить подход с дообучением трансформера на русскоязычных данных. Исследования с LLM показывают, что на выявление неоднозначности влияют примеры в запросе [7] и доступный модели контекст проекта [16].

Гайдамака [2] количественно оценил простоту формулировок и провёл эксперимент по поиску противоречий. Куценок и Кораблев [5] использовали ГОСТ 34.602-2020 при выборе характеристик для извлечения и измерили F1 по каждой характеристике. Извлечение этих сведений и проверка наличия предусмотренных стандартом разделов требуют разной разметки. Тимощук [6] предложил модель измерения нескольких свойств русскоязычных требований и продемонстрировал прототип на примерах.

В рассмотренных публикациях не найдено единого протокола, по которому на одних и тех же русскоязычных ТЗ оценены и поиск дефектов отдельных требований с учётом контекста, и проверка наличия разделов, предусмотренных ГОСТ 34.602-2020 для ТЗ на автоматизированную систему. Этот сценарий рассматривается в проекте. Для каждого уровня будет своя единица разметки и своя оценка качества.

## 3. Обзор и сравнение аналогов

### Прямые аналоги

1. **QVscribe** — надстройка для проверки формулировок требований, в том числе по шаблонам EARS. Документация описывает интеграции с редакторами и системами управления требованиями. [Документация QRA](https://qracorp.com/qvscribe-features/)
2. **IBM Engineering Requirements Quality Assistant** — анализатор требований с интеграцией в DOORS. В независимом исследовании на автомобильных требованиях авторы отметили ограниченность синтаксических проверок для задач Bosch [15]. [Документация IBM](https://www.ibm.com/docs/en/erqa?topic=assistant-guidelines-good-requirements)
3. **Jama Connect Advisor** — проверка формулировок в Jama Connect по рекомендациям INCOSE и шаблонам EARS. [Документация Jama Software](https://www.jamasoftware.com/platform/jama-connect/jama-connect-advisor/)
4. **Smella** [8] — исследовательский инструмент для поиска признаков дефектов формулировок с помощью правил. Авторы оценивали совпадение предупреждений с результатами ручной проверки.
5. **Прототип Е.В. Тимощука** [6] — реализация метрик для русскоязычных требований с использованием сторонних NLP-инструментов и внешнего API.

### Косвенные аналоги

1. **Чат с LLM с разовым запросом «проверь требования»** — пользователь может передать текст и запросить замечания. Критерии, примеры и контекст зависят от запроса. Исследования [7, 16] оценивают конкретные модели и режимы с заданными инструкциями и метриками. Их результаты применимы в пределах описанных экспериментов.
2. **«Главред»** — подсвечивает стоп-слова и предлагает рекомендации по стилю русскоязычного текста. [Описание сервиса](https://glvrd.ru/)
3. **Шаблоны страниц Confluence** — помогают задать общую структуру документа для ручного заполнения и последующего ревью.

### Выводы по сравнению

Из существующих решений можно взять:
- оценку каждого требования по шкале с подсветкой проблемных слов (QVscribe, IBM RQA);
- проверку по шаблонам EARS и правилам INCOSE (Jama Connect Advisor, QVscribe);
- статический анализ по ISO 29148 (Smella);
- метрики для русского языка (прототип Тимощука);
- объяснения на естественном языке (LLM).

В изученных материалах по аналогам не подтверждена комбинация двух возможностей: выявление дефектов русскоязычных требований с пояснением и проверка наличия разделов ТЗ по ГОСТ 34.602-2020. Для оценки прототипа можно использовать идеи двух экспериментов: фиксировать примеры и способ их отбора [7], а влияние контекста проверять при одинаковых критериях неоднозначности [16].

## 4. Итоги

**Итоговая тема ВКР:** Разработка интеллектуальной системы анализа качества требований к программному обеспечению на основе методов обработки естественного языка

**УДК для тезиса:** 004.912:004.41

**Ключевые слова:** инженерия требований, качество требований, обработка естественного языка, неоднозначность требований, классификация требований, техническое задание, языковые модели

### Актуальность исследования

При ручном рецензировании ТЗ аналитик проверяет, как сформулированы отдельные требования и все ли предусмотренные разделы присутствуют. Подсветка подозрительных фрагментов и список отсутствующих разделов могут помочь быстрее находить места, требующие внимания. Систематический обзор [17] показывает, что обнаружение проблем в спецификациях относится к основным задачам NLP в инженерии требований.

Эксперименты по оценке простоты требований [2], извлечению характеристик из ТЗ [5] и выявлению неоднозначности с учётом контекста [7, 16] дают основания проверить эти подходы на русскоязычных ТЗ. Для выбранного сценария остаётся открытым вопрос, с каким качеством методы обнаруживают дефекты формулировок и пропущенные разделы на документах из проектов, которые не использовались при настройке системы. Именно эти две задачи предполагается проверить в составе одного прототипа.

### Цель исследования

Разработать прототип для поддержки рецензирования русскоязычных ТЗ. Прототип должен выявлять и пояснять дефекты отдельных требований к ПО, классифицировать требования и проверять наличие разделов по ГОСТ 34.602-2020 в ТЗ на автоматизированные системы. Качество поиска дефектов и проверки структуры планируется оценить раздельно.

### Задачи исследования

1. Изучить стандарты (ISO/IEC/IEEE 29148, ГОСТ 34.602-2020, ГОСТ Р ИСО/МЭК 25010) и существующие подходы, составить модель качества и перечень типичных дефектов русскоязычных требований.
2. Собрать корпус русскоязычных требований на основе открытых ТЗ из ЕИС. Описать признаки неоднозначности, неполноты и непроверяемости, единицы разметки и порядок разбора спорных случаев. Для проверки структуры отдельно размечать наличие ожидаемых разделов. При использовании переводных наборов данных учитывать исходный документ и его переводы как одну группу.
3. Реализовать модуль правил: поиск «слабых» слов и конструкций с учётом морфологии, проверку структуры ТЗ.
4. Обучить и сравнить модели классификации требований (TF-IDF + SVM, RuBERT) и поиска неоднозначностей (RuBERT, LLM с примерами в запросе и контекстом документа).
5. Разработать прототип с веб-интерфейсом: загрузка документа, подсветка проблем, объяснения, итоговый отчёт.
6. Разделить данные по исходным документам или проектам, чтобы похожие формулировки и переводы из одной группы оставались в одной части выборки. Отдельно оценить обнаружение дефектов требований и наличие разделов ТЗ по precision, recall и F1. При сравнении с ручной проверкой измерять также затраченное время.
